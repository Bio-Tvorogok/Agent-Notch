# Сервисы

«Настройки → Сервисы» запускают и настраивают локальные программы, у которых есть манифест для Agent Notch. Раздел ничего не знает о конкретной программе: форму, команды и файлы даёт манифест, строки состояния — форма файла состояния. Первым сервисом подключён Гоша (Discord-бот, `~/Documents/Projects/chedrik`), его контракт — `docs/agent-notch.md` в его репозитории.

## Как добавить

«Добавить сервис…» → папка, в которой лежит `ops/agent-notch.json` (или `agent-notch.json` в корне). Приложение читает манифест и показывает id, папку, откуда идёт запуск, каждую команду с аргументами (и настоящий путь программы, если имя ведёт по ссылке), какие из них получают настройки и какие файлы читаются для состояния и логов. Сервис добавляется только после «Добавить»; Return окно не подтверждает. Если файл манифеста потом изменится хоть на байт, раздел покажет «Манифест изменился»: ничего не запускается и файлы состояния и логов не читаются, пока изменения не подтвердят снова. В окне повторного подтверждения новые, изменённые и убранные команды помечены.

Подтверждается текст манифеста. Программам внутри папки приложение доверяет как есть: правка `ops/gosha` подтверждения не требует, как и обновление любой программы после `git pull`.

## Манифест, версия 1

| Поле | Что это |
|---|---|
| `manifest` | версия схемы, `1` |
| `id` | `^[a-z0-9][a-z0-9._-]{0,63}$`; имя записи в связке ключей |
| `name`, `description` | имя в списке и строка под ним; строка или подписи на языках (ниже) |
| `cwd` | папка, из которой запускаются команды, относительно папки сервиса; по умолчанию `.` |
| `settings` | `{ "via": "fd", "fd": 3 }`: настройки идут JSON-ом в дескриптор `fd` (3–9) |
| `fields[]` | поля формы |
| `commands` | имя → `{ run, config?, json?, label?, timeout? }` |
| `status` | файл состояния |
| `logs` | имя → файл лога |

Пути `status` и `logs`: `~/…` (домашняя папка), абсолютный путь или путь относительно папки сервиса. Неизвестные поля верхнего уровня пропускаются.

### Подписи на языках

`name`, `description`, `label` (у полей, вариантов и команд), `help` и `placeholder` — строка или объект `{ "ru": "…", "en": "…" }`. Приложение берёт свой язык (язык системы), затем региональный вариант (`ru-RU`), затем английский, затем первый язык по имени. Ключи — коды языков (`^[a-z]{2,3}(-[A-Za-z0-9]{2,8})?$`), проверяется каждый вариант, а не только показанный. Отпечаток подтверждения от языка не зависит: подтверждается файл.

### Поля

| Свойство | Что это |
|---|---|
| `key` | имя настройки, `^[A-Za-z_][A-Za-z0-9_]{0,63}$` |
| `label`, `help`, `placeholder` | подписи в форме, одной строкой; строка или подписи на языках |
| `type` | `string`, `secret` или `select` |
| `required` | без значения Start и Restart недоступны |
| `pattern` | регулярное выражение, ищется в значении (как `RegExp.test`); якоря `^…$` ставит сам манифест |
| `default` | значение по умолчанию; у `secret` его нет, у `select` со списком оно должно быть в списке |
| `options` | для `select`: `values` — `[{ value, label }]`, или `command` — команда из `commands` с `json: true`, которая печатает JSON-массив |
| `when` | показывать поле, только пока другие поля имеют нужные значения: `{ "VOICE_TTS": "voicestudio" }` или `{ "MODE": ["a", "b"] }`. Скрытое поле не обязательно, не проверяется и в дескриптор не уходит (как и то, что заполнил его выбор), но сохранённое значение остаётся. Условие только на несекретные поля и не на само поле; цепочки условий можно, круги нельзя |

У `options.command` ещё есть `value` и `label` (имена полей объектов в ответе), `enabledWhen` (поле, которое должно быть `true`, чтобы вариант можно было выбрать) и `sets`: что записать в другие настройки при выборе, например `{ "claude": { "CLAUDE_BIN": "path" } }`. Поля объектов `method` (или `detail`) и `version` показываются под выбором, `login` — как подсказка для варианта без входа. Приложение не запускает `login`: это не команда манифеста.

`loginCommand` — вход по кнопке: значение варианта → имя команды манифеста, например `{ "codex": "codex-login" }`. Рядом с вариантом, который нельзя выбрать (`enabledWhen` ложно), появляется «Войти», запускающая эту команду. Команда должна быть из `commands` и не из служебных (`start`, `stop`, `restart`, `status`, `check-pc`, `providers`).

### Команды

`run` — массив аргументов без оболочки. `run[0]` — программа внутри папки сервиса, относительно `cwd`; после разрешения ссылок она должна остаться в папке. `config: true` — команда получает настройки. `needs` (только с `config: true`) — какие ключи она получает: поля и то, что заполняет выбор (`sets`); остальные в дескриптор не попадают, а из связки ключей для её настроек читаются только перечисленные секреты. Без `needs` команда получает все показанные поля, как раньше; `[]` — пустой объект. `json: true` — stdout — JSON. `timeout` — секунды, 1–3600, по умолчанию 180. `label` — подпись кнопки других команд; `start`, `stop`, `restart` и `status` всегда подписаны словами приложения, чтобы манифест не мог назвать «Остановить» запуском.

Кнопки раздела: `start`, `stop`, `restart`, `status` и «Проверка» для `check-pc`. Каждая другая команда манифеста (у Гоши `codex-login`) — кнопка в блоке «Команды» с её `label` или именем: индикатор, пока идёт, тайм-аут из манифеста, код выхода и вывод со скрытыми секретами. Когда такая команда закончилась, приложение заново спрашивает варианты у `options.command`, поэтому вход сразу виден в выборе. Команда из `options.command` (у Гоши `providers`) запускается сама, когда открываются настройки сервиса, и по кнопке «Обновить». Start, Stop и Restart ждут друг друга; остальные команды идут параллельно с ними, так что десятиминутный вход не мешает остановить сервис. Start и Restart требуют заполненных обязательных полей из тех, что они получают; остальные команды с `config: true` получают то, что заполнено, поэтому проверка работает и до заполнения всей формы. `check-pc` печатает `{ ok, url, healthMs, latencyMs, error }`; если JSON нет, показывается последняя строка stderr.

## Как запускается команда

- Перед каждым запуском манифест читается заново и сверяется с подтверждённым (SHA-256 текста). Программа ещё раз разрешается и должна лежать в папке сервиса.
- Манифест, папка сервиса, `cwd` и программа должны принадлежать пользователю (или root) и не быть доступными на запись группе и остальным ни по правам, ни по ACL: запись ACL, разрешающая изменение, отклоняется, запрещающие (как `everyone deny delete` на папках дома) не мешают. Интерпретатор из `#!` и программы, которые сервис находит через PATH, не проверяются.
- Регулярные выражения манифеста при разборе не выполняются: шаблон можно построить так, что проверка значения по умолчанию займёт минуты. Значение по умолчанию, не подходящее под шаблон, форма покажет как «Неверный формат».
- `posix_spawn`: stdin — `/dev/null`, stdout и stderr — каналы приложения, настройки — канал на дескрипторе из `settings.fd`. Объект пишется в канал целиком до запуска, конец приложения закрывается. Остальные дескрипторы приложения закрыты (`POSIX_SPAWN_CLOEXEC_DEFAULT`).
- Настройки не попадают ни в окружение, ни в аргументы, ни на диск. В канал идут только показанные поля (`when`) и только ключи из `needs`, если они есть.
- Окружение: `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`, `__CF_USER_TEXT_ENCODING` и `PATH`, который выдаёт оболочка входа пользователя (`$SHELL -l -c`). У приложения из Dock `PATH` — только `/usr/bin:/bin:/usr/sbin:/sbin`, а node и CLI обычно лежат в других местах. Ничего другого из окружения приложения сервис не получает: ни `CLAUDECODE`, ни ключей API.
- Команда работает в своей группе процессов; по тайм-ауту группа получает SIGTERM, через 3 с (или когда команда уже вышла) SIGKILL. Демон, который команда оставила держать её вывод, ждём не дольше секунды после выхода команды.
- PATH оболочки входа запоминается на время работы приложения, только если оболочка ответила за 5 с; запасной PATH не запоминается. `zsh -l` читает `.zshenv` и `.zprofile`, но не `.zshrc`.

## Файл состояния

Приложение читает `status` раз в 2 секунды, пока открыт раздел, и только у подтверждённого манифеста. Файлы состояния и логов открываются без блокировки и без перехода по ссылке в последнем звене пути; читается только обычный файл (FIFO, `/dev/zero` и устройства отклоняются), состояние — до 256 КБ, лог — последние 64 КБ. Сервис считается запущенным, если процесс `pid` жив, принадлежит пользователю и запущен не позже `startedAt` (плюс 5 с): так чужой процесс, получивший тот же pid, не выглядит сервисом. Кроме `pid`, `startedAt`, `updatedAt` и `lastError` каждый объект верхнего уровня становится строкой, по форме:

| Форма | Строка |
|---|---|
| `{ "online": bool, "servers": [{ "name", "answers" }] }` | в сети или нет, серверы; `answers: false` помечается |
| `{ "enabled": bool, "in": { "channelName", "guildName" } \| null }` | где сервис, «вне голоса», «выключен» |
| `{ "provider": string, "alive": bool }` | провайдер и готов ли он |
| `{ "ok": bool \| null, "url": string }` | работает, не работает, ещё не проверено |

Ключи `discord`, `voice`, `brain`, `tts`, `stt` идут первыми и подписаны по-человечески; остальные — по имени ключа (только `[A-Za-z0-9_-]`, до 32 символов).

## Секреты

Поля `secret` хранятся только в связке ключей входа: generic password, сервис `com.forichok.agents-notch.service.<id>.<12 знаков SHA-256 папки>`, аккаунт — `key` поля. Папка в имени нужна, чтобы другая папка с тем же `id` не получила чужие секреты. При сохранении запись удаляется и создаётся заново: заранее подложенная запись не сохранит свой список доступа. После сохранения значение не показывается, раздел знает только, что оно есть. В UserDefaults (`services`) лежат папка, отпечаток подтверждённого манифеста, что запускали его команды, несекретные значения и «запускать вместе с приложением»; `ServiceEntry` отказывается записывать в себя ключ секретного поля. «Удалить сервис…» удаляет все записи этого сервиса в связке ключей, в том числе ключи, которых в манифесте уже нет; при повторном подтверждении удаляются секреты убранных полей. Файлы сервиса и запущенный сервис остаются.

Чего связка ключей не даёт. Список доступа записи называет приложение по подписи, а у сборки с ad-hoc подписью это только идентификатор пакета. Программа того же пользователя, подписанная тем же идентификатором, прочитает секрет без вопроса. Секрет получит и программа в папке сервиса, если её заменить, и папка, подставленная в настройки приложения вместе с отпечатком. Связка ключей защищает секреты от диска, настроек, логов и чужих учётных записей, но не от кода, работающего от имени пользователя. Настоящую защиту дала бы подпись Developer ID.

Всё, что приложение показывает из сервиса (`lastError`, строки состояния: серверы, каналы, провайдер и адреса, вывод команд, ошибка проверки, варианты выбора и подсказки входа, хвост логов), проходит маскировку: сохранённые секреты заменяются на `***`, где бы они ни встретились, а также всё, что похоже на токен Discord, ключи Anthropic, OpenAI и GitHub, `Bearer …`, `token=…`, `api_key: …` и пароль в URL. Маскировка работает за линейное время и вне главного потока; строка показывается не длиннее 2000 символов уже после маскировки. Секрет, записанный в лог в JSON-экранированном или URL-кодированном виде, буквально не совпадёт и скроется, только если похож на один из шаблонов.

## Проверка

- `scripts/test.sh`: `service*` в `Tests/CoreChecks` — разбор манифеста Гоши, отказ кривым манифестам (ссылки из папки, права и ACL, невидимые символы, FIFO вместо манифеста), форма и JSON настроек, варианты из `providers`, канал в дескрипторе 3 на крошечном скрипте, который читает fd 3, утечка дескрипторов, окружение, тайм-аут с убийством всей группы, повторное подтверждение, файл состояния, специальные файлы, проверка, хвост и маскировка логов (в том числе время на враждебных строках), секреты по папке.
- `AgentsNotch --snapshot-services <папка>` (из корня репозитория) рисует раздел на подставном сервисе на обоих языках: пустой, окно подтверждения, работающий и остановленный.
